# 3. 구현 세부 사항

## 3-1. 웹사이트의 색상을 추출하는 로직은 어떻게 구현 할까?

처음에는 단순히 웹사이트에서 CSS 속성을 가져오면 색상을 분석할 수 있을 것이라 생각했습니다. 하지만 막상 구현을 시작하고 보니, 웹사이트마다 스타일이 적용되는 방식이 다르고, 단순히 색상 값을 가져오는 것만으로는 대표 색상을 도출하기 어려웠습니다.

각 요소에 적용된 색상이 모두 동일한 중요도를 가지는 것도 아니었고, `getComputedStyle()`을 사용해 색상을 추출해도 중복된 데이터, 의미 없는 색상, 투명한 요소 등이 포함되는 문제가 있었습니다. 따라서 중요한 색상만 남기고 대표 색상을 뽑아내는 과정이 필요했습니다.

이를 해결하기 위해 색상 추출 과정을 다음과 같은 네 가지 단계로 정리했습니다.

1. 웹사이트의 스타일 데이터를 크롤링하여 색상 정보를 수집한다.
2. 수집한 색상 데이터를 정제하고 불필요한 색상을 필터링한다.
3. 의미 있는 색상을 판별하여 중요도를 반영한다.
4. 대표 색상을 선정하여 최종 결과로 제공한다.

**크롤링을 통한 웹사이트 색상 데이터 수집**

웹사이트에서 색상을 추출하는 과정은 단순히 CSS 속성을 가져오는 것이 아니라, 실제로 화면에 렌더링된 색상을 정확하게 파악하는 것이 핵심이었습니다. 웹사이트마다 스타일 적용 방식이 다르기 때문에, 인라인 스타일에서 색상을 가져오는 것 만으로는 충분하지 않았습니다. CSS 파일에 정의된 색상, `var(--custom-color)` 같은 변수로 선언된 스타일, 그리고 여러 스타일 규칙이 중첩될 때 최종적으로 적용되는 색상까지 모두 고려해야 했습니다. 이를 위해 브라우저가 계산한 최종 스타일 값을 가져오는 방식이 필요했고, `getComputedStyle()`을 활용하여 요소별로 실제 적용된 색상을 추출했습니다. 또한, 단순히 모든 요소의 색상을 가져오는 것이 아니라, `display: none`이나 `opacity: 0`처럼 보이지 않는 요소는 제외하고, 동일한 색상이 반복되는 경우 중복을 줄이는 방식으로 크롤링을 최적화했습니다. 처음에는 iframe이나 Shadow DOM 내부의 스타일까지 포함하려 했지만, Shadow DOM은 접근이 어렵고 일부 웹사이트에서는 `closed` 상태로 설정되어 있어 외부에서 데이터를 가져오는 것이 불가능했습니다. 그래서 현재는 일반적인 DOM을 대상으로 색상을 추출하는 방식으로 구현했습니다.

**수집된 색상 데이터의 정제 및 전처리**

색상을 가져온 후에는 그대로 사용할 수 있는 것이 아니라 정제하는 과정이 필요했습니다. `getComputedStyle()`을 사용하면 브라우저가 색상을 자동으로 `rgb(r, g, b)` 형식으로 변환해 반환하기 때문에 추가적인 변환 과정은 필요하지 않았습니다. 하지만 불필요한 색상을 걸러내는 것이 중요한 작업이었습니다. 예를 들어, `display: none`이나 `visibility: hidden`이 적용된 요소는 화면에 보이지 않기 때문에 대표 색상을 결정하는 데 영향을 주지 않도록 필터링했습니다. 중복된 색상도 하나로 합쳐야 했습니다. 웹사이트의 스타일 구조상 같은 색상이 여러 번 등장하는 경우가 많았기 때문에, 동일한 색상을 여러 개 포함하면 대표 색상을 선정할 때 왜곡이 발생할 수 있었습니다. 따라서 유사한 색상을 하나로 묶는 과정을 거쳐 분석의 정확도를 높였습니다.

이렇게 정제된 색상 데이터라도 웹사이트에서 모든 색상이 같은 중요도를 가지는 것은 아니기 때문에, 어떤 색상이 더 중요한지를 판별하는 과정이 필요했습니다. 예를 들어, 웹사이트의 배경색과 로고 색상이 같은 비중으로 반영되는 것은 적절하지 않았습니다. 특히, 본문 텍스트나 버튼의 색상처럼 사용자 경험(UX)에 직접적인 영향을 주는 색상이 상대적으로 더 중요하다고 판단했습니다. 또한, 특정 UI 요소에서 사용된 색상을 더 높은 가중치로 반영해야 했습니다. 제목(`h1, h2`), 네비게이션 바(`nav`), 버튼(`button`) 같은 요소에 적용된 색상은 페이지의 핵심적인 부분을 차지하므로, 단순한 구분선이나 작은 아이콘보다 더 높은 우선순위로 처리되었습니다. 색상이 적용된 요소의 크기도 고려해야 했습니다. 웹사이트에서 차지하는 면적이 큰 색상일수록 대표 색상으로 선정될 가능성이 높아야 했고, 작은 아이콘이나 배경 이미지에서 일부 포함된 색상은 상대적으로 낮은 우선순위를 가지도록 조정했습니다. 이렇게 중요도를 고려한 색상 필터링을 통해 실제 웹사이트를 대표하는 색상을 보다 정확하게 선정할 수 있었습니다.

마지막으로, 최종적으로 선정할 대표 색상을 결정하는 과정이 필요했습니다. 단순히 가장 많이 등장하는 색상을 대표 색상으로 지정하는 방식은 적절하지 않았습니다. 예를 들어, 웹사이트의 배경색이 흰색이라면 가장 많이 등장하는 색상이 흰색이 될 수 있지만, 이것이 대표 색상이 될 필요는 없었습니다. 이를 해결하기 위해 K-means Clustering 알고리즘을 활용하여 색상을 그룹화했습니다. 비슷한 색상끼리 묶어서 대표 색상을 추출하고, 웹사이트에서 차지하는 비중을 고려해 중요한 색상을 선정하는 방식이었습니다. 또한, 아주 작은 비율로 포함된 색상은 대표 색상으로 반영되지 않도록 필터링하여, 의미 있는 색상만 남길 수 있도록 했습니다. 이렇게 선정된 대표 색상은 단순한 색상 데이터가 아니라, 웹사이트의 브랜드 컬러 분석, 디자인 최적화, 색상 트렌드 연구 등 다양한 용도로 활용할 수 있었습니다.

## 3-2. 어떻게 하면 웹사이트에서 의미 있는 색상을 찾을 수 있을까?

처음 색상 추출 기능을 개발할 때는 단순히 `getComputedStyle()`을 이용해 웹사이트에서 사용된 모든 색상을 가져오면 된다고 생각했습니다. 하지만 그렇게 가져온 색상 데이터는 너무 많고, 정작 웹사이트를 대표하는 색상을 찾기에는 부적절했습니다.

예를 들어, 웹사이트의 가장 중요한 색상은 로고나 주요 버튼, 제목 등에 사용된 색상이 될 가능성이 높은데, 단순히 등장 빈도만으로 대표 색상을 선정하면 웹사이트의 배경색이나 작은 아이콘의 색상이 대표 색상으로 뽑히는 문제가 발생했습니다. 이렇게 단순 빈도 분석만으로는 의미 있는 색상을 추출하기 어렵다는 점이 큰 도전 과제였습니다. 결국, 모든 색상을 같은 비중으로 다루면 안 되고, 특정 요소에 더 높은 중요도를 부여하는 방식이 필요하다는 결론에 도달했습니다.

### 발생한 문제: 웹사이트의 대표 색상으로 의미 없는 색상이 선정되는 문제

```jsx
if (
              propertyValue &&
              (propertyName.includes("color") ||
                propertyName.includes("Color") ||
                propertyName.includes("COLOR") ||
                propertyValue.includes("rgb") ||
                propertyValue.includes("RGB") ||
                propertyValue.includes("!important"))
            ) {
              if (
                allCssPropertiesOfElement.getPropertyValue("display") === "none" ||
                allCssPropertiesOfElement.getPropertyValue("visibility") === "hidden"
              ) {
                continue;
              }
```

이 문제를 해결하기 위해, 먼저 어떤 요소가 중요한지 판단하는 기준을 만들었습니다. 일반적으로 텍스트 색상과 배경색이 있을 때, 텍스트 색상이 더 중요한 경우가 많았고, 제목(h1, h2) 같은 요소는 일반 본문 텍스트보다 더 높은 가중치를 가져야 했습니다. 또한, 버튼(button), 네비게이션 바(nav), 헤더(header)처럼 웹사이트에서 중요한 역할을 하는 요소의 색상도 우선적으로 고려해야 했습니다. 반대로, `display: none`, `visibility: hidden`처럼 보이지 않는 요소의 색상은 대표 색상 선정에 반영하지 않도록 했습니다. 이런 기준을 설정한 후, 중요한 요소에 가중치를 반영하는 방식으로 데이터를 조정해야 했습니다.

**해결 방법 : 가중치 기반 색상 증강(Augmentation) 기법 적용**

여기서 활용한 개념이 **데이터 증강(Data Augmentation)**이었습니다. 머신러닝분야에서 모델을 개발할 때 특정 데이터를 증강시켜 모델의 학습 효과를 높이는 것처럼, 중요도가 높은 색상을 인위적으로 여러 번 리스트에 추가하여 대표 색상 분석에 더 큰 영향을 미치도록 했습니다. 예를 들어, 제목(h1, h2), 버튼(button), 로고나 파비콘(favicon)과 유사한 색상이 있으면 200번 반복하여 추가하는 식이었습니다. 단순 빈도 기반 분석이 아니라, 디자인적으로 중요한 요소의 색상을 더욱 강조할 수 있도록 데이터를 조작하는 방식이었습니다.

![Image](https://github.com/user-attachments/assets/c4d37513-49f5-4d65-8a6e-e42d23878904)

이 방식을 적용하자, 대표 색상 분석 결과가 훨씬 안정적으로 나왔습니다. 단순히 가장 많이 등장하는 색상이 아니라, 실제로 웹사이트에서 중요한 색상이 대표 색상으로 선정되는 비율이 증가했고, 배경색이 너무 강하게 반영되는 문제도 완화되었습니다. 하지만 여전히 한계는 있었습니다. 웹사이트마다 중요한 요소가 다를 수 있어 특정 요소에 가중치를 부여하는 방식이 항상 적절한 것은 아니었고, 디자인이 단순한 경우에는 배경색이 강하게 반영될 가능성이 있었습니다. 또한, 다크 모드를 지원하는 웹사이트에서는 별도의 처리가 필요했기 때문에, UI 패턴을 자동으로 분석하고, 웹사이트 구조에 따라 가중치를 동적으로 조정하는 방식도 고려할 필요가 있었습니다. 하지만 현재 구현한 방식만으로도 단순히 `getComputedStyle()`로 모든 색상을 가져와서 분석하는 것보다 훨씬 의미 있는 색상 데이터를 도출할 수 있었고, 웹사이트의 핵심 색상을 보다 정확하게 반영할 수 있었습니다.

## 3-3. 발생한 문제: CSS 데이터 수집의 복잡성

처음에는 `getComputedStyle()`을 이용하면 모든 요소의 스타일을 쉽게 가져올 수 있을 거라고 생각했습니다. 하지만 실제로 구현을 진행하면서 웹사이트의 스타일 데이터를 정확하게 수집하는 것이 예상보다 훨씬 복잡하다는 사실을 깨달았습니다. 웹사이트마다 CSS가 적용되는 방식이 다르고, 스타일이 여러 계층에서 결정되며, 크롤링을 통해 이를 수집하는 과정에서 다양한 예외 상황이 발생했기 때문입니다. 단순히 `document.querySelectorAll("*")`을 사용해 모든 요소를 선택하고 `getComputedStyle()`을 호출하는 것만으로는 해결되지 않는 문제들이 있었고, 이를 하나씩 해결해 나가야 했습니다.

처음 마주한 문제는 CSS 스타일이 여러 위치에서 정의된다는 점이었습니다. 스타일은 인라인(`style="color: red;"`), 내부 스타일(`style` 태그), 외부 스타일(`link` 태그를 통해 로드된 CSS 파일)에서 정의될 수 있고, 심지어 CSS 변수(`var(--primary-color)`)로 설정되기도 했습니다. 문제는 `getComputedStyle()`을 사용하면 브라우저에서 최종적으로 적용된 스타일만 가져올 수 있어서, 원본 스타일이 어디에서 정의되었는지 알 수 없다는 것이었습니다. 처음에는 CSS 파일을 직접 분석하는 방식도 고려했지만, 웹사이트가 외부 CSS 파일을 여러 개 로드하거나 동적으로 스타일을 변경하는 경우가 많아 실용적이지 않았습니다. 따라서 결국 `getComputedStyle()`을 활용하여 최종 렌더링된 스타일 값을 가져오는 방식을 선택했습니다. 하지만 여기서 또 다른 문제가 있었습니다.

### 해결 방법: 부모 요소와 비교하여 상속된 스타일 필터링

웹사이트의 스타일은 부모 요소로부터 상속되기도 하고, 특정 조건에 따라 동적으로 변경되기도 합니다. 예를 들어, 텍스트 색상(`color`)은 부모 요소의 영향을 받을 수 있으며, 다크 모드 지원 웹사이트에서는 `prefers-color-scheme`을 기반으로 스타일이 변경되기도 합니다. 단순히 `getComputedStyle()`을 호출하면 현재 적용된 스타일 값만 가져올 수 있을 뿐, 해당 스타일이 직접 지정된 것인지, 부모 요소에서 상속된 것인지 구별할 수 없었습니다. 이런 문제를 해결하기 위해, 원본 스타일과 비교하여 상속된 스타일을 구별하는 방식을 도입했습니다.

```jsx
const isInheritedColor = (element, propertyName) => {
  if (!element.parentElement) {
    return false;
  }

  const computedStyle = window.getComputedStyle(element);
  const parentStyle = window.getComputedStyle(element.parentElement);

  const inlineStyle = element.style.getPropertyValue(propertyName);

  return (
    computedStyle.getPropertyValue(propertyName) ===
      parentStyle.getPropertyValue(propertyName) && !inlineStyle
  );
};
```

구체적으로, 먼저 `getComputedStyle()`을 사용하여 현재 요소의 스타일을 가져온 후, 부모 요소(`element.parentElement`)의 `getComputedStyle()` 값을 비교하는 방식으로 접근했습니다. 만약 부모 요소와 같은 `color` 값을 가진다면, 이는 상속된 색상일 가능성이 높았고, 이러한 색상은 대표 색상 선정 과정에서 중요도를 낮추는 방식으로 처리했습니다. 하지만 단순히 부모 요소와 동일한 색상이라고 해서 무조건 상속된 값으로 간주할 수는 없었습니다. 어떤 경우에는 자식 요소가 직접 같은 색상을 설정했을 수도 있기 때문입니다. 이를 구별하기 위해 `element.style.color` 값을 추가로 확인하여, 만약 요소의 `style` 속성에서 직접 색상이 지정되지 않았다면 상속된 색상으로 판단하는 방식을 적용했습니다.

## 3-6. 현재 확인한 문제점과 개선 방향

웹사이트에서 색상을 추출하고 대표 색상을 분석하는 과정에서 여러 가지 최적화와 개선 작업을 거쳤지만, 여전히 보완해야 할 부분이 남아 있었습니다. 초기 구현에서는 `getComputedStyle()`을 활용해 모든 요소의 색상을 가져온 후 K-means Clustering을 사용해 대표 색상을 도출하는 방식이었지만, 특정 상황에서는 여전히 부정확한 색상 분석 결과가 나오는 문제가 있었습니다. 또한, 크롤링 과정의 성능을 개선했음에도 불구하고, 웹사이트 크기에 따라 크롤링 시간이 과도하게 증가하는 문제도 완전히 해결되지 않았습니다. 이를 해결하기 위해 현재 인지하고 있는 문제점을 정리하고, 향후 개선 방향을 고민해 보았습니다.

### 3-6-1. 대표 색상 선정 과정에서의 문제: 특정 색상이 과도하게 반영되는 현상

현재 대표 색상을 선정하는 과정에서 가장 큰 문제 중 하나는 웹사이트의 배경색이 대표 색상으로 너무 자주 선정되는 현상입니다. 일반적으로 웹사이트의 배경색은 가장 많이 등장하는 색상이기 때문에, K-means Clustering을 적용하면 배경색이 대표 색상으로 도출될 확률이 높았습니다. 하지만 웹사이트를 대표하는 색상이 반드시 배경색이어야 하는 것은 아니었고, 헤더, 버튼, 링크 등의 색상이 더 중요한 경우도 많았기 때문에, 단순한 등장 빈도만으로 대표 색상을 결정하는 방식은 보완이 필요했습니다.

이를 해결하기 위해, 대표 색상을 선정할 때 배경색의 영향을 낮추고, UI에서 의미 있는 색상을 강조하는 방식을 도입할 필요가 있습니다. 예를 들어, 배경색이 지나치게 많이 등장하는 경우 이를 자동으로 필터링하는 로직을 추가하거나, K-means Clustering을 적용하기 전에 특정 요소의 색상 비중을 인위적으로 높이는 방식을 적용할 수도 있습니다. 기존에 적용했던 데이터 증강 기법을 더 정교하게 개선하여, 중요도가 높은 요소에 포함된 색상이 더욱 강하게 반영될 수 있도록 수정할 계획입니다.

### 3-6-2. 크롤링 속도 문제: 대규모 웹사이트에서 실행 시간이 너무 오래 걸리는 문제

웹사이트에서 색상을 추출하는 과정에서 가장 큰 문제 중 하나는 웹사이트의 크기에 따라 크롤링 속도가 선형적으로 증가한다는 점이었습니다. 작은 웹사이트에서는 1~2초 내로 크롤링이 완료되었지만, 복잡한 웹사이트에서는 10초 이상 소요되는 경우도 있었습니다. 특히, `getComputedStyle()`을 호출하는 부분이 성능 저하의 주요 원인이었습니다.

기본적으로 `querySelectorAll("*")`을 사용해 모든 요소를 한꺼번에 가져온 후, 각 요소에 대해 `getComputedStyle()`을 호출하여 색상 데이터를 수집하는 방식이었습니다. 이론적으로 `getComputedStyle()`을 한 번 호출하는 데 걸리는 시간은 O(1)이라고 볼 수 있지만, 실제로는 브라우저 렌더링 엔진과 상호작용하는 과정에서 성능 비용이 발생하기 때문에 요소 개수가 많아질수록 실행 시간이 선형적으로 증가했습니다. 즉, 요소 개수가 `N`개일 때, 크롤링의 시간복잡도는 O(N)이었으며, `getComputedStyle()`을 호출하는 과정이 많아질수록 성능이 급격히 저하되는 문제가 있었습니다.

또한, Puppeteer를 이용해 크롤링을 수행할 때, 브라우저를 새로 실행할 때마다 초기 로딩 시간이 발생하는 문제도 있었습니다. Puppeteer는 기본적으로 크롬 브라우저를 실행한 후 웹사이트를 로드하고, 페이지의 DOM을 분석하는 방식으로 동작하기 때문에, 브라우저를 매번 새로 실행하는 방식은 초기 로딩 시간과 메모리 사용량 증가로 이어졌습니다. 특히, 여러 개의 크롤링 요청을 동시에 처리할 경우, 브라우저 인스턴스를 여러 개 띄우게 되면서 서버 부하가 급격하게 증가하는 문제도 발생했습니다.

이를 해결하기 위해, 크롤링을 캐싱하는 방식을 고려할 수 있었습니다. 동일한 웹사이트에 대한 크롤링 요청이 반복될 경우, 이전 크롤링 결과를 일정 시간 동안 저장해두고, 동일한 요청이 들어오면 기존 데이터를 반환하는 방식입니다. 이렇게 하면 불필요한 크롤링 요청을 줄일 수 있으며, 이미 분석된 웹사이트라면 즉시 응답을 반환할 수 있기 때문에 크롤링 속도를 대폭 단축할 수 있습니다.

또한, Puppeteer를 실행할 때 브라우저를 새로 띄우는 방식 대신, 하나의 브라우저 인스턴스를 유지한 채 여러 개의 페이지를 생성하여 실행하는 방식으로 변경하면 성능을 더욱 최적화할 수 있습니다. 기존 방식에서는 크롤링할 때마다 Puppeteer가 새로운 브라우저를 실행하는 방식이었지만, 하나의 Puppeteer 브라우저 인스턴스를 유지하면서 여러 개의 `page` 객체를 생성해 크롤링을 수행하면 브라우저 초기화 시간을 줄이고, 메모리 사용량을 최소화할 수 있습니다.

이러한 최적화를 적용하면 크롤링 속도를 개선할 수 있으며, 특히 반복적인 크롤링 요청이 많은 경우 서버 리소스를 절약하는 효과도 기대할 수 있습니다. 하지만 여전히 크롤링 속도를 더 높이기 위해 불필요한 요소를 필터링하는 방식이나 `getComputedStyle()` 호출을 최소화하는 추가적인 개선이 필요할 것으로 보였습니다.

### 3-6-3. 다크 모드 지원 웹사이트에서의 색상 추출 문제

현대 웹사이트들은 대부분 다크 모드를 지원하는 경우가 많으며, `prefers-color-scheme: dark`와 같은 CSS 속성을 사용하여 스타일을 변경하는 방식이 일반적이었습니다. 하지만 현재 크롤링 방식에서는 웹사이트의 다크 모드 색상을 고려하지 않고 기본 색상만 분석하는 문제가 있었습니다. 이로 인해, 다크 모드에서 디자인이 달라지는 웹사이트에서는 대표 색상이 정확하게 추출되지 않는 경우가 발생했습니다.

```jsx
await page.emulateMediaFeatures([
  { name: "prefers-color-scheme", value: "dark" },
]);
await page.evaluate(() => matchMedia("(prefers-color-scheme: dark)").matches);

await page.evaluate(() => matchMedia("(prefers-color-scheme: light)").matches);
```

이 문제를 해결하기 위해, 크롤링할 때 다크 모드를 적용한 상태에서 색상을 분석하는 방식을 추가할 수 있습니다. Puppeteer를 사용할 때 `page.emulateMediaFeatures([{ name: "prefers-color-scheme", value: "dark" }])`와 같은 기능을 이용하면, 웹사이트를 다크 모드로 렌더링한 상태에서 `getComputedStyle()`을 호출할 수 있기 때문에, 보다 정확한 색상 분석이 가능해집니다. 이를 적용하면 다크 모드와 라이트 모드에서 각각 대표 색상을 추출할 수 있으며, 두 모드 간의 색상 변화를 비교하는 것도 가능해집니다.

### 3-6-4. 특정 웹사이트에서 크롤링이 차단되는 문제

일부 웹사이트에서는 Puppeteer를 이용한 자동화 크롤링을 감지하고, `navigator.webdriver = true` 값을 기반으로 크롤링을 차단하는 경우가 있었습니다. 또한, 특정 웹사이트에서는 CSP(Content Security Policy)를 활용하여 외부 스크립트 실행을 제한하는 방식으로 크롤링을 막고 있었으며, 이러한 경우에는 기존 방식으로 색상을 추출할 수 없었습니다.

이를 해결하기 위해, Puppeteer Stealth 플러그인을 활용하여 자동화 탐지를 우회하는 방식을 적용할 수 있습니다. Puppeteer Stealth 플러그인은 웹사이트가 Puppeteer를 탐지하는 일반적인 패턴을 피하도록 설정할 수 있으며, `navigator.webdriver = false`로 설정하여 크롤링 탐지를 우회할 수 있습니다. 또한, 크롤링 요청의 User-Agent를 실제 브라우저와 동일하게 변경하고, 헤드리스 모드(headless: false)를 설정하여 보다 자연스럽게 크롤링을 수행하는 방식도 적용할 수 있습니다.

## 3-7. CSS 상속 개념을 고려한 색상 추출 방식과 문제 해결

### 3-7-1. css 상속

웹사이트에서 색상을 추출하는 과정에서 가장 까다로웠던 부분 중 하나는 CSS 상속이었습니다. 처음에는 단순히 `getComputedStyle()`을 이용하면 요소별로 적용된 색상을 정확하게 가져올 수 있을 거라 생각했지만, 실제로 구현을 진행하면서 부모 요소에서 상속된 색상과 직접 지정된 색상을 구별하는 것이 필요하다는 점을 깨달았습니다. 예를 들어, 웹사이트의 본문에 적용된 텍스트 색상이 `body` 요소에 설정되어 있는 경우, 해당 색상은 모든 자식 요소에 상속되지만, 개별적인 요소에서 다른 색상을 직접 지정했을 수도 있습니다. 이러한 차이를 무시하고 색상을 분석하면, 실제 웹사이트의 디자인을 반영하지 못하는 대표 색상 분석 결과가 나올 가능성이 높았습니다.

기본적으로 `getComputedStyle()`을 사용하면 브라우저에서 최종적으로 적용된 스타일 값을 반환하기 때문에, 이 값이 부모 요소에서 상속된 것인지, 해당 요소에서 직접 지정된 것인지 구별할 수 없습니다. 즉, 단순히 `getComputedStyle().color` 값을 가져와 분석하면, 상속된 색상까지 그대로 반영될 가능성이 높아지고, 특정 요소에 직접 설정된 색상이 덜 중요하게 취급될 수도 있습니다. 이 문제를 해결하기 위해, 부모 요소와 자식 요소 간의 색상 상속 여부를 구별하는 방법이 필요했습니다.

### 3-7-2. 부모 요소와 색상을 비교하는 방식

가장 먼저 시도한 방법은, 부모 요소의 `getComputedStyle()` 값과 현재 요소의 `getComputedStyle()` 값을 비교하는 방식이었습니다. 만약 두 값이 같다면, 이는 부모 요소로부터 상속된 색상일 가능성이 높다고 판단할 수 있습니다. 하지만 이 방식만으로는 완벽하지 않았습니다. 특정 요소가 부모와 동일한 색상을 가지고 있더라도, 이는 단순히 같은 색상으로 설정된 것이지 반드시 상속된 색상이라고 단정할 수는 없었기 때문입니다. 예를 들어, `<p>` 요소가 `body` 요소와 같은 색상을 사용한다고 해서, 무조건 `body`에서 상속받았다고 볼 수는 없었습니다.

### 3-7-3. `style` 속성을 확인하여 상속 여부 구별

이 문제를 해결하기 위해, 현재 요소의 `style` 속성을 추가로 확인하는 방식을 도입했습니다. 즉, `element.style.color` 값을 확인하여, 만약 요소가 직접 스타일을 지정한 경우라면, 부모 요소와 동일한 색상이더라도 상속된 것으로 간주하지 않는 방식입니다. 이 방식을 적용하면, 자식 요소가 직접 색상을 지정한 경우와 단순히 상속된 경우를 효과적으로 구별할 수 있었고, 대표 색상을 선정할 때 상속된 색상이 과도하게 반영되는 문제를 해결할 수 있었습니다. 하지만 여기서 또 다른 문제가 있었습니다. 웹사이트의 스타일은 `inherit`, `unset`, `initial` 같은 CSS 키워드를 사용하여 의도적으로 상속을 조작할 수도 있다는 점이었습니다. 이런 경우, `getComputedStyle()`을 사용해도 상속 여부를 정확하게 판별할 수 없었습니다. 이를 해결하기 위해, `window.getComputedStyle(element).getPropertyValue("color")` 값을 가져올 때, `element.style.color`뿐만 아니라 `element.hasAttribute("style")`을 함께 확인하여, 해당 요소가 인라인 스타일을 포함하고 있는지 여부를 추가로 체크하는 방식을 적용했습니다. 이를 통해 `inherit`을 사용한 경우에도 보다 정교한 분석이 가능해졌습니다.

## 3-8. K-means Clustering을 이용한 대표 색상 추출 방식과 문제 해결

웹사이트에서 색상을 추출한 후, 가장 중요한 과정 중 하나는 대표 색상을 선정하는 것이었습니다. 단순히 가장 많이 등장한 색상을 대표 색상으로 선정하는 방식은 적절하지 않았습니다. 예를 들어, 웹사이트의 배경색이 흰색(`rgb(255, 255, 255)`)이라면, 가장 많이 등장하는 색상이 흰색이 될 가능성이 높았지만, 이것이 웹사이트의 대표 색상이라고 보기에는 어려웠습니다. 또한, 텍스트 색상이나 버튼 색상처럼 디자인적으로 중요한 색상들이 대표 색상에서 누락되는 문제도 발생할 수 있었습니다. 이를 해결하기 위해, K-means Clustering(이하 K-means)을 적용하여 비슷한 색상을 그룹화하고, 가장 의미 있는 대표 색상을 선정하는 방식을 도입했습니다.

### 3-8-1. K-means Clustering이란?

![Image](https://github.com/user-attachments/assets/f30f7f88-e745-4124-b564-3b1acca7a291)

K-means는 데이터 포인트들을 K개의 그룹(클러스터)으로 나누는 비지도 학습(unsupervised learning) 알고리즘으로, 초기에는 K개의 중심점을 랜덤하게 설정한 후, 각 데이터 포인트를 가장 가까운 중심점에 할당하여 클러스터를 형성한 뒤, 각 클러스터의 평균을 계산하여 새로운 중심점을 설정하는 과정을 반복하는 방식으로 작동합니다. 이를 색상 분석에 적용하면 비슷한 색상들을 하나의 그룹으로 묶고, 각 그룹의 대표 색상을 선정할 수 있었습니다.

### 3-8-2. 발생한 문제: K-means의 초기 중심점 설정 문제

**K 값을 얼마로 설정해야 하는가?**

하지만 이를 적용하는 과정에서 몇 가지 문제가 있었습니다. 우선 K 값을 얼마로 설정해야 하는지가 문제였습니다. K-means는 미리 군집(K) 개수를 지정해야 하는데, 웹사이트마다 적절한 K 값이 다를 수 있었고, K 값이 너무 크면 쓸데없이 많은 대표 색상이 추출되었고, 너무 작으면 웹사이트의 핵심 색상이 누락될 가능성이 있었습니다.

**초기 중심점 설정에 따라 결과가 달라지는 문제**

또한, K-means는 초기 중심점을 랜덤하게 설정하기 때문에, 실행할 때마다 결과가 달라질 가능성이 있었고, 같은 웹사이트에서도 대표 색상이 달라질 수 있어 일관된 결과를 보장하기 어려웠습니다.

**대표 색상이 실제 웹사이트의 핵심 색상과 다를 수 있음**

게다가, K-means는 단순히 색상의 수학적 거리(유클리디안 거리)를 기반으로 그룹을 형성하기 때문에, 웹사이트의 디자인적 맥락을 고려하지 않는 문제가 있었습니다. 즉, 웹사이트의 로고 색상이 디자인적으로 중요한 색상일 수 있지만, K-means는 단순히 색상의 빈도를 기준으로 클러스터를 형성하기 때문에 로고 색상이 적절하게 반영되지 않는 경우도 발생했습니다.

### 3-8-3. 초기 중심점 설정 문제 해결을 위한 개선 방향

**K 값 동적 설정**

이 문제를 해결하기 위해 K 값을 자동으로 조정하는 방식을 도입할 예정입니다. 웹사이트마다 적절한 K 값을 자동으로 조정하기 위해 엘보우 메서드(Elbow Method)와 실루엣 점수(Silhouette Score) 같은 기법을 사용하여 최적의 K 값을 찾을 예정입니다.

**K-means++ 초기화 적용**

또한, K-means의 초기 중심점 설정 문제를 해결하기 위해 K-means++ 초기화 방식을 사용하여 보다 안정적인 클러스터링 결과를 보장할 예정입니다. 기존 방식에서는 랜덤하게 초기 중심점을 설정했기 때문에 대표 색상이 일관되지 않았지만, K-means++을 적용하면 첫 번째 중심점을 랜덤하게 선택한 후, 이전 중심점들과 거리가 먼 데이터 포인트를 중심점으로 설정하는 방식으로 보다 정교한 결과를 얻을 수 있을 것 같습니다.

## 3-9. AWS EC2 배포

웹사이트에서 색상을 크롤링하고 분석하는 기능을 AWS EC2 환경에서 배포하는 과정에서 여러 가지 문제가 발생했습니다. 초기에는 단순히 서버 코드를 EC2에 올리고 실행하면 원활하게 동작할 것이라 생각했지만, Puppeteer를 이용한 크롤링 작업을 실행하는 과정에서 환경 설정 문제, 메모리 부족 문제, 그리고 CI/CD 구축 과정에서 발생하는 이슈들이 겹치면서 정상적으로 동작하지 않는 경우가 많았습니다. 이를 해결하기 위해 EC2 환경에서의 크롤링 최적화, 메모리 관리, 그리고 배포 자동화 방안을 고려하며 문제를 해결해야 했습니다.

### 3-9-1. Puppeteer가 EC2에서 정상적으로 실행되지 않는 문제

가장 먼저 직면한 문제는 Puppeteer를 EC2에서 실행할 때 브라우저가 정상적으로 실행되지 않는 문제였습니다. Puppeteer는 기본적으로 Chromium을 내부적으로 실행하여 웹페이지를 렌더링하고 크롤링하는데, EC2와 같은 클라우드 환경에서는 GUI 환경이 없기 때문에, 기본적인 설정만으로는 브라우저가 실행되지 않았습니다. 이를 해결하기 위해, Puppeteer를 실행할 때 `--no-sandbox` 옵션과 `--disable-setuid-sandbox` 옵션을 추가하여 보안 샌드박스 기능을 비활성화하는 방식을 적용했습니다. 또한, EC2 인스턴스에서는 Puppeteer 실행에 필요한 라이브러리가 기본적으로 설치되어 있지 않기 때문에, `chromium`, `libnss3` 등의 필수 패키지를 수동으로 설치해야 했습니다. 이러한 설정을 마친 후에야 Puppeteer가 정상적으로 실행될 수 있었습니다.

### 3-9-2. 메모리 부족 문제 및 Swap 메모리 설정 계획

그 다음으로 해결해야 했던 문제는 EC2에서 실행할 때 메모리 부족으로 인해 크롤링 작업이 중간에 실패하는 문제였습니다. 현재 EC2는 프리 티어 계정으로 새, 기본적으로 t2.micro 인스턴스를 사용하고 있기 때문에, Puppeteer가 브라우저를 실행할 때 메모리 사용량이 급격히 증가하면 크롤링이 비정상적으로 종료되는 현상이 발생했습니다. 특히, 한 번에 여러 개의 크롤링 요청이 들어오는 경우에는 메모리 부족 현상이 더욱 두드러졌습니다. 이를 해결하기 위해 Swap 메모리를 설정하여 부족한 RAM을 가상 메모리로 보충하는 방식을 적용할 계획입니다. Swap 메모리를 설정하면 RAM이 부족할 때 일부 데이터를 디스크로 이동시켜 추가적인 메모리 공간을 확보할 수 있으며, 이를 통해 Puppeteer가 크롤링 중간에 종료되지 않고 안정적으로 실행될 가능성이 높아집니다.

### 3-9-3. 배포 과정 개선 및 CI/CD 구축 계획

배포 과정에서도 몇 가지 개선이 필요했습니다. 현재는 수동으로 서버에 코드를 배포하고 실행하는 방식이었지만, 빌드 및 배포 자동화를 위해 Jenkins를 이용한 CI/CD 구축을 계획하고 있습니다. Jenkins를 활용하면 코드 변경 사항이 있을 때 자동으로 빌드하고, EC2에 배포하여 최신 버전의 서버가 항상 운영될 수 있도록 설정할 수 있습니다. CI/CD를 구축하면 배포 과정에서 발생할 수 있는 수동 작업을 줄일 수 있으며, 코드 변경 사항이 반영될 때마다 자동으로 테스트와 배포가 이루어지도록 설정할 수 있습니다. 이를 통해 크롤링 서비스의 유지보수성을 높이고, 코드 변경이 있을 때 더 빠르고 안정적으로 배포할 수 있는 환경을 만들 계획입니다.
